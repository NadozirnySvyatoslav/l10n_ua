## 1. Загальний опис та нормативне обґрунтування

У PR #411 (#322) було реалізовано первинну перевірку наявності заяви через булевий прапорець `psp_application` на моделі `hr.version` (контракті).

Задача #415 реалізує заяву про застосування ПСП як окремий документ (`hr.psp.application`) з фіксацією розміру пільги відповідно до чинної термінології системи, дати подання та дати закінчення згідно з нормами ст. 169 Податкового кодексу України:
1. **пп. 169.2.1 ПКУ:** ПСП застосовується виключно за **одним місцем** нарахування (виплати) заробітної плати.
2. **пп. 169.2.2 ПКУ:** Платник податку самостійно обирає місце та розмір ПСП і подає роботодавцю заяву. ПСП починає застосовуватися до нарахованих доходів **з місяця отримання заяви**.
3. **пп. 169.2.3 ПКУ:** Застосування ПСП **зупиняється з місяця, в якому подано заяву про відмову (дата закінчення)** або припинено трудові відносини. **У місяць дати закінчення ПСП уже не нараховується.**
4. **пп. 169.2.4 ПКУ:** Заборона одночасного застосування ПСП за кількома місцями роботи/картками фізичної особи в межах усієї бази даних.
5. **пп. 169.1.1 ПКУ:** ПСП застосовується виключно до заробітної плати (договори ЦПХ, гіг-контракти та авторські договори пільги не мають).

## 2. Архітектура моделі `hr.psp.application`

### 2.1. Структура полів моделі

| Поле | Тип | Властивості | Призначення |
| :--- | :--- | :--- | :--- |
| `name` | Char | required, copy=False, default=New | Номер заяви (генерується послідовністю `ir.sequence`) |
| `employee_id` | Many2one | 'hr.employee', required, ondelete='restrict', index=True | Працівник, який подає заяву |
| `company_id` | Many2one | 'res.company', required, default=self.env.company, index=True | Компанія-роботодавець |
| `rnokpp` | Char | related='employee_id.rnokpp', store=True, index=True, readonly=True | РНОКПП (ІПН) фізичної особи для глобальної перевірки |
| `state` | Selection | default='draft', tracking=True | **Статус**: `draft` (Чернетка), `active` (Чинна) |
| `psp_type` | Selection | required, default='standard' | **Розмір ПСП** (значення чинної системи):<br>• `standard` — «Стандартна (50%)»<br>• `150` — «150%»<br>• `200` — «200%» |
| `date_from` | Date | required, default=today, string="Дата подання" | Дата подання заяви. ПСП діє починаючи з місяця цієї дати |
| `date_to` | Date | string="Дата закінчення" | Дата закінчення / відмови. **У місяць цієї дати ПСП уже не нараховується** |
| `active` | Boolean | default=True | Стандартний прапорець активності запису (архівування) |
| `note` | Text | string="Підстава та підтвердні документи" | Текстовий опис підстави (пільга на дітей, інвалідність тощо) та перелік доданих документів |
| `attachment_ids` | Many2many | 'ir.attachment' | Скани заяви та підтвердних документів |

### 2.2. Життєвий цикл документа (`state`)
- `draft` (Чернетка):
  - Початковий стан при створенні заяви. Документ доступний для вільного редагування.
  - Кнопка **«Підтвердити» (`action_activate`)**: переводить у стан `active`. При цьому виконується валідація наявності РНОКПП та відсутності перетинів з іншими чинними заявами особи по всій базі.
- `active` (Чинна):
  - Заява бере участь у розрахунку зарплати за відповідні місяці.
  - Кнопка **«Повернути в чернетку» (`action_draft`)**: повертає на редагування.
  - Поле **«Дата закінчення» (`date_to`)**: заповнюється у разі відмови/закінчення дії заяви.

## 3. Правила перевірки та валідації (Constraints)

### 3.1. Валідація дат у документі
- Якщо `date_to` заповнено, обов'язково: `date_to >= date_from`.

### 3.2. Контроль «Один РНОКПП — одна чинна заява в періоді»
- Перевірка виконується по всій базі даних (`sudo()`) серед заяв у стані `active`.
- **Розрахунковий період дії заяви в місяцях:**
  - Початок: місяць дати подання `date_from.replace(day=1)`.
  - Завершення:
    - якщо `date_to` не заповнено: безстроково;
    - якщо `date_to` заповнено: оскільки в місяць дати закінчення ПСП уже не нараховується, останнім місяцем дії є місяць, що передує місяцю `date_to`.
- Дві активні заяви для одного `rnokpp` не можуть мати перетину періодів.
- При виявленні перетину генерується `ValidationError` із номером конфліктної заяви, назвою компанії та ПІБ співробітника.
- Для затвердження заяви обов'язкова наявність заповненого РНОКПП у працівника.

## 4. Інтеграція з розрахунковим листом (`hr.payslip`) та `hr.version`

### 4.1. Алгоритм розрахунку ПСП у `hr.payslip`
1. **Перевірка типу договору:**
   - Якщо договір працівника належить до `PSP_NON_SALARY_CONTRACT_TYPES` (`civil`, `gig`, `author`) — ПСП не застосовується (`psp_type = 'none'`), оскільки це не заробітна плата (пп. 169.1.1 ПКУ).
2. **Пошук чинної заяви на розрахунковий місяць:**
   - Шукається активна заява (`state == 'active'`) для працівника `payslip.employee_id`:
     - `date_from <= payslip.date_to` (подана не пізніше розрахункового місяця);
     - `date_to` не заповнена АБО `date_to.replace(day=1) > payslip.date_to` (місяць закінчення строго пізніший за розрахунковий місяць, оскільки в місяць закінчення ПСП уже не нараховується).
3. **Визначення типу та суми ПСП:**
   - Якщо чинна заява є:
     - `payslip.psp_type = application.psp_type` (береться зафіксоване в заяві значення: `standard`, `150`, `200`).
     - `payslip.psp_application_id = application.id` (фіксується посилання на документ заяви).
   - Якщо заяви немає:
     - `payslip.psp_type = 'none'`, `payslip.psp_application_id = False`.
4. Метод `_compute_psp` розраховує граничний дохід та суму пільги `psp_amount` на основі визначеного `payslip.psp_type` та кількості дітей/пільг працівника.

### 4.2. Поле `hr.version.psp_application` (Compute)
- Поле `psp_application` на моделі `hr.version` залишається як обчислюване (`compute='_compute_psp_application'`).
- **Логіка розрахунку:** повертає `True`, якщо для працівника існує активна заява `hr.psp.application`, **чинна на поточну дату** (`fields.Date.context_today(self)`).

   - Посилання `psp_application_id` на чинну заяву місяця.

## 6. Друкована форма заяви (QWeb Report)

- Шаблон PDF-звіту «Заява про застосування податкової соціальної пільги» за типовою формою наказу ДПА № 761.
- **Зміст друкованої форми:**
  - Шапка: назва підприємства, посада та ПІБ керівника.
  - Заявник: ПІБ працівника, РНОКПП, посада, адреса.
  - **Текст заяви:** прохання застосовувати ПСП у зафіксованому розмірі (`standard` — «Стандартна (50%)», `150` — «150%», `200` — «200%») відповідно до норм ст. 169 ПКУ.
  - **Підстава та підтвердні документи:** вивід тексту з поля `note`.
  - Дата подання, підпис працівника.

## 7. План тестування (Test Plan)

1. **Тест життєвого циклу (`draft` → `active`):**
   - У стані `draft` заява не впливає на розрахунковий лист (`psp_type = 'none'`).
   - Після активації заява підтягується в розрахунковий лист.
2. **Тест застосування розміру ПСП із заяви:**
   - Заява з `psp_type = 'standard'` → `payslip.psp_type = 'standard'`.
   - Заява з `psp_type = '150'` → `payslip.psp_type = '150'`.
   - Заява з `psp_type = '200'` → `payslip.psp_type = '200'`.
3. **Тест дат подання та закінчення (`date_from`, `date_to`):**
   - Подання 20 червня → ПСП нараховується за весь червень.
   - Дата закінчення 10 липня → за червень ПСП є, за липень ПСП **вже не нараховується**.
4. **Тест міжкомпанійної унікальності за РНОКПП:**
   - Дві активні заяви на однаковий період для одного РНОКПП (в одній або різних компаніях) блокуються валідатором.
5. **Тест ЦПХ/гіг-договорів:**
   - Навіть за наявності чинної заяви договір ЦПХ/гіг не отримує ПСП.
6. **Тест `hr.version.psp_application`:**
   - Повертає `True`, якщо на поточну дату є чинна активна заява, і `False` за її відсутності.
