> договір із НСЗУ з розрахунком капітації. Сценарій орієнтований на демо-сервер

> тестування.

## 0. Застосунок і налаштування закладу

Меню застосунків → **Медицина (UA)**. Верхнє меню: **Пацієнти**, **Декларації**, **Прийоми**,
**Договори НСЗУ**, **Пакети НСЗУ**, **МКХ-10**, **Хронічні стани**, **Алергії**, **Налаштування**.

Перед стартом заповніть **реквізити закладу** (модуль `base`) у картці компанії:

| Поле | Значення (приклад) |
|------|--------------------|
| Тип закладу | ЦПМСД _(13 типів: АСМД, поліклініка, лікарня, пологовий, ЕМД, діагностичний центр, реабілітація, санаторій, диспансер, лабораторія, аптека, інше)_ |
| Форма власності | Комунальна _(або державна)_ |
| Номер / дата ліцензії МОЗ | напр. `АЕ-123456` / 01.01.2024 |
| ID надавача в НСЗУ | ідентифікатор закладу в НСЗУ |
| ID в eHealth | ідентифікатор у ЕСОЗ |
| Спеціалізації | з довідника **Налаштування → Спеціалізації** (13 стартових записів) |

> _Скриншот:_ `00-menu.png`

**Встановлення модулів:**

```bash
# Ядро (збірка): база + пацієнти + НСЗУ
./venv311/bin/odoo -d odoo19ndev -i l10n_ua_medecin --stop-after-init

# Повний стек (з клінічною карткою та eHealth)
./venv311/bin/odoo -d odoo19ndev -i l10n_ua_medecin,l10n_ua_medecin_clinical,l10n_ua_medecin_ehealth --stop-after-init
```

> `clinical` та `ehealth` у збірку `l10n_ua_medecin` **не входять** — їх встановлюють окремо.

## Флоу 1. Картка пацієнта

> Реєстрація пацієнта із авто-обчисленням віку й вікової категорії — саме категорія визначає
> капітаційний коефіцієнт (Флоу 4). Модель `l10n_ua.medecin.patient`.

### Крок 1. Створити картку пацієнта

**Медицина (UA) → Пацієнти → кнопка `Новий`.** Заповніть поля:

| Поле | Значення (приклад) |
|------|--------------------|
| Фізособа | контакт `res.partner` — ПІБ, адреса, контакти тут (напр. _Іваненко Іван Іванович_) |
| Номер мед.картки | `А-000123` _(унікальний у межах закладу)_ |
| Заклад | ТОВ «Тестова Компанія» _(за замовчуванням поточна компанія)_ |
| Дата народження | 15.03.1985 |
| РНОКПП | `2855012345` _(10 цифр; для дітей до 14 р. — порожнє, натомість свідоцтво про народження)_ |
| Свідоцтво про народження | лише для дітей до 14 років |
| Стать | Чоловіча / Жіноча |

### Крок 2. Перевірити авто-обчислення (результат введення)

Після збереження система **одразу обчислює** з дати народження:

| Показник | Результат (для 15.03.1985) |
|----------|---------------------------|
| **Вік** | 41 _(на поточну дату)_ |
| **Вікова категорія** | **40–64 років** _(зберігається, `store=True`)_ |
| Поточна декларація | _порожньо_ — заповниться з активної декларації (Флоу 2) |
| Поточний лікар | _порожньо_ — підтягнеться з активної декларації |

**5 вікових категорій** (межі: `<=5`, `<=17`, `<=39`, `<=64`, решта):

| Категорія | Вік |
|-----------|-----|
| 0–5 | 0…5 |
| 6–17 | 6…17 |
| 18–39 | 18…39 |
| 40–64 | 40…64 |
| 65+ | 65 і старше |

**Валідація РНОКПП:** якщо ввести не 10 цифр — система відхилить збереження з помилкою
_«РНОКПП має бути 10-значним числом»_. **Унікальність картки:** повторний номер медкартки в
тому самому закладі заблокується (constraint `unique(patient_card_no, company_id)`).

Картка має чатер (`mail.thread`) для історії змін.

> _Скриншоти:_ `01-patients-list.png`, `02-patient-form.png`

## Флоу 2. Декларація ПМД (вибір лікаря)

> Декларація пацієнт↔лікар первинної медичної допомоги за **Наказом МОЗ № 503**. Саме
> **активні** декларації є базою розрахунку капітації (Флоу 4). Модель
> `l10n_ua.medecin.declaration`. Життєвий цикл: **Чернетка → Активна → Припинена / Скасована**.

### Крок 1. Створити декларацію

**Медицина (UA) → Декларації → кнопка `Новий`** (або кнопка з картки пацієнта). Заповніть:

| Поле | Значення (приклад) |
|------|--------------------|
| Номер | _присвоюється автоматично (`ir.sequence`) при збереженні_ |
| Пацієнт | Іваненко Іван Іванович (№А-000123) |
| Лікар | лікар ПМД (`hr.employee`) |
| Дата підписання | 10.07.2026 |
| Дата набуття чинності | 10.07.2026 |
| Ознака електронного підпису | так/ні |

Стан після створення — **Чернетка**. Дати валідуються (набуття чинності не раніше підписання
тощо).

### Крок 2. Активувати декларацію

Натисніть **`Активувати`** (`action_activate`). Результат:

- статус **Чернетка → Активна**;
- **попередня активна декларація того самого пацієнта автоматично припиняється** — у пацієнта
  може бути **лише одна діюча декларація** (перевірено тестом);
- у **картці пацієнта** обчислювані поля **Поточна декларація** та **Поточний лікар** тепер
  заповнені цією декларацією;
- (за встановленого `ehealth`) спрацьовує хук реєстрації в eHealth — у dry-run записується
  **псевдо-UUID** (див. Флоу 5).

### Крок 3. Результат: активна декларація

| Дія | Стан → | Ефект |
|-----|--------|-------|
| **Активувати** | Активна | авто-припинення попередньої, заповнення поточного лікаря пацієнта |
| **Припинити** (`action_terminate`) | Припинена | **вимагає підстави припинення** (інакше помилка) |
| **Скасувати** (`action_cancel`) | Скасована | декларація анульована |

Поле **UUID в eHealth** — унікальне, заповнюється при реєстрації (Флоу 5).

> _Скриншоти:_ `03-declaration-form.png`, `04-declaration-activate.png`

## Флоу 3. Клінічна картка: прийом і діагнози

> Потрібен модуль `l10n_ua_medecin_clinical` (у збірку **не входить**). Модель прийому —
> `l10n_ua.medecin.encounter`. Стани: **Заплановано → У процесі → Завершено / Скасовано**.
> Модуль **не покритий тестами**.

### Крок 1. Створити прийом

**Медицина (UA) → Прийоми → кнопка `Новий`.** Заповніть:

| Поле | Значення (приклад) |
|------|--------------------|
| Пацієнт | Іваненко Іван Іванович |
| Тип прийому | Консультація _(6 типів: профогляд, виклик додому, невідкладна, маніпуляція, діагностика)_ |
| Скарги / Огляд / Лікування | Html-поля (текст прийому) |

Стан після створення — **Заплановано**.

### Крок 2. Провести прийом (стани)

| Кнопка | Стан → |
|--------|--------|
| **`Розпочати`** (`action_start`) | У процесі |
| **`Завершити`** (`action_finish`) | Завершено |
| **`Скасувати`** (`action_cancel`) | Скасовано |

### Крок 3. Додати діагнози МКХ-10 (результат введення)

На вкладці діагнозів додайте рядки (`l10n_ua.medecin.diagnosis`):

| Поле | Значення (приклад) |
|------|--------------------|
| МКХ-10 | код із довідника `l10n_ua.medecin.icd10` (напр. `J06.9` — гостра інфекція верхніх дихальних шляхів) |
| Основний | так — головний діагноз прийому |
| Хронічний | так/ні |

Довідник **МКХ-10** — повний класифікатор НК 025:2021 (ICD-10-AM), ієрархічний
(`l10n_ua.medecin.icd10`, `_parent_store`, унікальність коду). У діагнозі можна обрати лише
код найнижчого рівня (фільтр «Допустимі як діагноз»): напр. не `J06`, а `J06.9`. Шукати можна
за початком коду або фрагментом назви.

> _Скриншоти:_ `05-encounter-form.png`, `06-icd10.png`

### Крок 4. Хронічні стани (проблемний лист пацієнта)

> Хронічні діагнози ведуться **окремо від прийому** — це health-summary пацієнта. Модель
> `l10n_ua.medecin.condition`. Модуль **без тестів**.

**Медицина (UA) → Хронічні стани → кнопка `Новий`** (окреме верхнє меню, `action_condition`).
Заповніть рядок:

| Поле | Модель-поле | Значення (приклад) |
|------|-------------|--------------------|
| Пацієнт | `patient_id` | Іваненко Іван Іванович _(обов'язково)_ |
| МКХ-10 | `icd10_id` | `I10` — гіпертонічна хвороба _(обов'язково)_ |
| Дата встановлення | `date_onset` | _за замовч. сьогодні (`context_today`)_ |
| Дата зняття | `date_resolved` | _порожньо, доки стан активний_ |
| Хронічний | `is_chronic` | так _(за замовчуванням `True`)_ |
| Ступінь | `severity` | Легка / Помірна / Тяжка (`mild`/`moderate`/`severe`) |
| Примітка | `note` | вільний текст |

**Результат:** запис прив'язується до пацієнта (`ondelete='cascade'`), сортування — за датою
встановлення (спадання). Окремих обчислень чи автопідстановок у прийом **немає** — це самостійний
довідниковий список.

### Крок 5. Алергії пацієнта (анамнез)

> Реєстр алергій `l10n_ua.medecin.allergy` — разом із хронічними станами формує клінічно значущий
> анамнез. Тести відсутні.

**Медицина (UA) → Алергії → кнопка `Новий`** (окреме верхнє меню, `action_allergy`). Заповніть:

| Поле | Модель-поле | Значення (приклад) |
|------|-------------|--------------------|
| Пацієнт | `patient_id` | Іваненко Іван Іванович _(обов'язково)_ |
| Алерген | `allergen` | Пеніцилін _(обов'язково, текст)_ |
| Тяжкість реакції | `severity` | Легка / Помірна / Тяжка (анафілаксія) — `mild`/`moderate`/`severe`, за замовч. `mild` |
| Реакція | `reaction` | «Кропивниця, набряк» _(вільний текст)_ |
| Примітка | `note` | вільний текст |

**Результат:** запис прив'язаний до пацієнта, сортування — за `patient_id, allergen`. Валідацій
дублікатів алергенів чи зв'язку з рецептами/призначеннями **немає** (eRx не реалізовано, див.
Флоу 5).

> Модулі `condition`/`allergy` **без тестів** — перед промисловим використанням потрібне
> покриття тестами.

## Флоу 4. Договір НСЗУ з капітацією

> Наскрізний процес «пакети → договір → капітація ПМД». Договір
> `l10n_ua.medecin.nszu.contract` (нумерація `НСЗУ-…`), життєвий цикл:
> **Чернетка → Подано → Активний → Завершений / Розірваний** (з поверненням у чернетку).
> Ядро покрите тестами.

### Крок 1. Створити договір із пакетами

Спершу переконайтесь, що є **пакети НСЗУ** (**Медицина (UA) → Пакети НСЗУ**,
`l10n_ua.medecin.nszu.package`, унікальні за парою **код + рік**; 10 типів, 5 моделей оплати,
5 стартових записів).

**Медицина (UA) → Договори НСЗУ → кнопка `Новий`.** Заповніть шапку:

| Поле | Значення (приклад) |
|------|--------------------|
| Номер | _авто (`НСЗУ-…`)_ |
| Номер договору НСЗУ | номер, присвоєний НСЗУ |
| Дата підписання / початку / закінчення | 01.01.2026 / 01.01.2026 / 31.12.2026 |

На вкладці **Пакети в договорі** додайте рядок (`l10n_ua.medecin.nszu.contract.line`):

| Поле | Значення (приклад) |
|------|--------------------|
| Пакет | «ПМД — капітація» _(модель оплати: **капітація**)_ |
| Тариф | базовий тариф пакета _(підставляється; можна змінити)_ |
| Очікувана кількість | 0 _(перерахуємо в кроці 3)_ |

**Результат введення рядка:** сума рядка = **тариф × очікувана кількість**
(`expected_amount`), а сума договору **Очікувані надходження** (`total_expected`) = Σ рядків —
обчислюються автоматично.

### Крок 2. Подати й активувати договір

| Кнопка | Стан → | Умова |
|--------|--------|-------|
| **`Подати`** (`action_submit`) | Чернетка → Подано | договір **повинен містити хоча б один пакет** — порожній подати не можна (перевірено тестом) |
| **`Активувати`** (`action_activate`) | Подано → Чинний | лише з поданого |
| **`Завершити`** (`action_expire`) | Чинний → Завершений | |
| **`Розірвати`** (`action_terminate`) | Поданий/Чинний → Розірваний | |
| **`У чернетку`** (`action_reset_to_draft`) | Поданий/Розірваний → Чернетка | |

### Крок 3. Розрахувати капітацію ПМД (результат)

На рядку пакета з моделлю оплати **капітація** натисніть **`Розрахувати капітацію ПМД`**
(`action_compute_pmd_capitation`). Система бере **активні декларації** закладу
(пацієнти з `active_declaration_id`), групує за **віковою категорією** й обчислює **зважену
кількість** за коефіцієнтами (приблизно за **Постановою № 240**):

| Вікова категорія | Коефіцієнт |
|------------------|-----------:|
| 0–5 | 4,0 |
| 6–17 | 2,2 |
| 18–39 | 1,0 |
| 40–64 | 1,2 |
| 65+ | 2,5 |

**Формула:** зважена кількість = Σ (кількість активних декларацій у категорії × коефіцієнт),
округлюється до цілого й записується в **Очікувану кількість** рядка. Приклад:

| Категорія | Активних декларацій | Коеф. | Зважено |
|-----------|--------------------:|------:|--------:|
| 0–5 | 10 | 4,0 | 40,0 |
| 18–39 | 100 | 1,0 | 100,0 |
| 65+ | 20 | 2,5 | 50,0 |
| **Разом** | **130** | | **190** → `expected_units = 190` |

Далі `expected_amount = тариф × 190`, а **Очікувані надходження** договору оновлюються. Коефіцієнти
за замовчуванням беруться з константи `AGE_COEFFICIENTS`, але **тариф і кількість у рядку можна
перевизначити вручну**.

> _Скриншоти:_ `07-nszu-package.png`, `08-nszu-contract.png`, `09-capitation.png`

## Флоу 5. Каркас eHealth: реєстрація декларацій (DRY-RUN)

> Потрібен модуль `l10n_ua_medecin_ehealth`. **Це каркас, а не робоча інтеграція** — реальну
> реєстрацію в ЕСОЗ на демо відтворити **не можна** (див. розділ «Поточний стан»).

**Налаштування API:** розділ налаштувань **eHealth** (`res.config.settings`) — URL, `client_id`,
`client_secret` і **прапорець dry-run**. За замовчуванням dry-run **увімкнено**: запити не йдуть
у ЕСОЗ, а пишуться в лог.

**Як працює:** при активації декларації (Флоу 2, `action_activate`) спрацьовує хук, який
намагається зареєструвати декларацію (`post_declaration` → `POST /api/declarations`). У dry-run
замість реального виклику генерується **псевдо-UUID**, який записується в поле декларації;
помилки реєстрації **не блокують** активацію.

**Журнал запитів:** **eHealth: лог запитів** (`l10n_ua.ehealth.request.log`) — усі
запити/відповіді API для аудиту.

> Реалізовано **лише** реєстрацію декларацій. Електронних рецептів (eRx) і направлень
> (eReferral) у коді **немає**.

> _Скриншоти:_ `10-ehealth-settings.png`, `11-ehealth-log.png`

## Флоу 6. Інші моделі оплати (не капітація) — ручний облік `[ЧАСТКОВО]`

> Пакет НСЗУ має **5 моделей оплати** (`PAYMENT_MODEL` у `l10n_ua_medecin_nszu_package.py`):
> **капітація** (`capitation`), **глобальний бюджет** (`global`), **за випадок** (`per_case`),
> **за послугу** (`per_service`), **змішана** (`mixed`). Автоматичний розрахунок реалізований
> **лише для капітації ПМД** (Флоу 4, крок 3). Для решти — ручне введення.

### Крок 1. Додати рядок пакета з не-капітаційною моделлю

На вкладці **Пакети в договорі** оберіть пакет із моделлю оплати, відмінною від капітації
(напр. «Стаціонарна» з моделлю **за випадок** `per_case`). Поле `payment_model` рядка —
`related` від `package_id.payment_model`, тож підставляється автоматично.

| Поле | Модель-поле | Значення (приклад) |
|------|-------------|--------------------|
| Пакет | `package_id` | «Стаціонарна — за випадок» |
| Модель оплати | `payment_model` | _за випадок (`per_case`) — тільки для читання, з пакета_ |
| Тариф | `tariff` | тариф за один випадок _(підставляється з `base_tariff`)_ |
| Очікувана кількість | `expected_units` | **вводиться вручну** — кількість випадків/послуг |

### Крок 2. Результат: суми рахуються, але кількість — ручна

- `expected_amount = tariff × expected_units` рахується автоматично
  (`_compute_expected_amount`) — **однаково для всіх моделей оплати**;
- `total_expected` договору оновлюється сумою рядків;
- **АЛЕ** кнопка **`Розрахувати капітацію ПМД`** (`action_compute_pmd_capitation`) для
  не-капітаційних рядків **нічого не робить** — метод містить `if line.payment_model !=
  'capitation': continue` і пропускає такий рядок.

### `[НЕ РЕАЛІЗОВАНО]` Погодинний / пооб'єктний облік наданих послуг

Окремого обліку **фактично наданих випадків або послуг** із прив'язкою до прийомів
(`l10n_ua.medecin.encounter`) чи діагнозів **немає**:

- прийоми (Флоу 3) **не агрегуються** у рядки договору НСЗУ — зв'язку encounter → contract.line
  у коді немає;
- немає моделі «наданої послуги/випадку» з тарифікацією, погодинного обліку чи реєстру виконаних
  робіт;
- для моделей `per_case`, `per_service`, `global`, `mixed` кількість завжди **вводить оператор
  вручну** у полі `expected_units`.

> Тобто для не-капітаційних пакетів модуль виконує роль **калькулятора очікуваних надходжень**, а
> не системи обліку наданих послуг.

## Флоу 7. Звітність до НСЗУ (реєстри / експорт) — `[НЕ РЕАЛІЗОВАНО]`

> Формалізованої **вивантажної звітності до НСЗУ** (реєстр декларацій, звіти про надані
> послуги/пакети, експорт у форматах ЕСОЗ) у коді **немає**. Нижче — чесний опис поточного стану
> й того, як така звітність мала б виглядати.

### Що є зараз (замість звітності)

- **Розрахунок очікуваних надходжень** договору: `total_expected` = Σ (`tariff × expected_units`)
  по рядках (Флоу 4). Це фінансова оцінка, а не поданий у НСЗУ реєстр.
- **Розрахунок капітації ПМД** (`action_compute_pmd_capitation`) — зважена кількість активних
  декларацій за віковими коефіцієнтами. Результат пишеться в `expected_units`, назовні **не
  вивантажується**.
- **Активні декларації** в картках пацієнтів (`active_declaration_id`) — джерело даних, з якого
  реєстр *міг би* формуватися.

### Чого немає

- моделі/дії формування **реєстру декларацій** для подання в НСЗУ;
- **звітів про надані послуги** за пакетами (per-case / per-service);
- **експорту** у структурованих форматах (XML/CSV/JSON), яких вимагає НСЗУ;
- жодного `ir.actions.report`, майстра вивантаження чи endpoint-а для НСЗУ-звітності.

### Як це має працювати (цільовий флоу, орієнтовно)

1. За звітний період система збирає **активні декларації** закладу (реєстр ПМД) та **надані
   випадки/послуги** за не-капітаційними пакетами.
2. Формує **реєстр** у форматі, визначеному НСЗУ, з підписанням **КЕП** уповноваженої особи.
3. Подає реєстр — на практиці **через Центральну компоненту eHealth**, а не прямою вивантажкою
   (обмін даними з НСЗУ йде через ЕСОЗ).
4. Зберігає квитанцію/статус обробки для аудиту.

> Оскільки реальний обмін іде через ЕСОЗ, ця звітність напряму залежить від робочої інтеграції
> eHealth — а вона наразі лише **dry-run каркас** (Флоу 5). Тож НСЗУ-звітність на демо
> відтворити **не можна**.

## Поточний стан

Фактичний стан домену на demo (звірено з кодом і аудитом):

- **Меню працює, демо-даних немає.** Застосунок і структура меню (Пацієнти, Декларації, Прийоми,
  Договори НСЗУ, Пакети НСЗУ, Хронічні стани, Алергії) встановлюються й відкриваються коректно,
  але **картки пацієнтів і договори НСЗУ порожні** — тож **капітацію наживо не звірено** (лише за
  кодом). Щоб пройти Флоу 1–4 наскрізь, базу треба спершу наповнити.
- **Ядро покрите тестами:** картка пацієнта, декларації ПМД, договори НСЗУ з капітацією
  (`l10n_ua_medecin_patient`, `l10n_ua_medecin_nszu`).
- **Клінічна картка — робоча** (`l10n_ua_medecin_clinical`); довідник МКХ-10 — повний
  класифікатор НК 025:2021 (без Зміни № 1 від 2024 р.).
- **eHealth — dry-run каркас** (`l10n_ua_medecin_ehealth`). Реєстрація декларацій генерує лише
  **псевдо-UUID**, **без реального ЕСОЗ**. Реальна реєстрація потребує підключення до Центральної
  компоненти eHealth, облікових даних МОЗ, робочого OAuth2 `client_credentials` та **КЕП** —
  після чого вимикають dry-run. На демо цього немає.
- **НСЗУ-облік — лише капітація ПМД + фінансова оцінка.** Автоматичний розрахунок кількості є
  тільки для моделі оплати `capitation`; для `per_case`/`per_service`/`global`/`mixed` кількість
  вводиться вручну (Флоу 6). **Обліку фактично наданих послуг** (прив'язка прийомів до договору,
  погодинний облік) і **формалізованої звітності/реєстрів для НСЗУ** з експортом **немає**
  (Флоу 7) — модуль рахує лише очікувані надходження договору.

**Технічна примітка:** `action_compute_pmd_capitation` використовує `read_group` зі старим ключем
`*_count`; на Odoo 19 метод варто перевести на `_read_group`.
